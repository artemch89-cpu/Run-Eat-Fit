# CLAUDE.md — Run Eat Fit

Читай этот файл первым при возврате к проекту. Полная спека — в `MVP-SPEC.md`, сырые материалы для методичек — в `research/`.

## Что это

Telegram-бот — персональный AI-тренер с памятью о жизни пользователя. Не калькулятор калорий (ниша занята — Calorie AI, FoodScan, FitnessAI Bot), дифференциация — живой коуч, который держит контекст жизни человека (стресс, перелёт, самочувствие) и подстраивает план под это.

## Статус

MVP-спека готова (07.09.2026). Скелет + анкета (не «онбординг» — так называть при общении с Артёмом) + диалог с коучем готовы (08.09.2026), тестируется живьём на аккаунте Артёма.

`/start` → анкета (цель → профиль нагрузки → стиль общения, кнопки → время чек-ина, текст ЧЧ:ММ) → после завершения обычный текст уходит в диалог с коучем (системный промпт из профиля юзера + текущая дата/время по Белграду, история в таблице `messages`). Ошибка API не роняет бота, юзер видит сообщение о сбое.

11.09.2026 (третий заход) — prompt-кэш системного промпта включён:
- `buildSystemPrompt` теперь отдаёт не строку, а массив из 3 блоков с двумя точками кэша (`cache_control: {type:'ephemeral'}`): (1) `FROZEN_INSTRUCTIONS`, (2) профиль+тест готовности+календарь плана, (3) без кэша — строка «Сейчас:» (меняется каждый запрос).
- **Важная находка:** у Haiku 4.5 минимальный кэшируемый префикс — 4096 токенов (у Sonnet/Opus 5 — 512-1024). Сам системный промпт (~3600 токенов) один этого порога не набирает — реально кэшируется только вместе с тремя tool-схемами (`tools` идут в префикс перед `system`), в сумме ~10800 токенов. Без tools в запросе (или если их станет меньше/короче) кэш может снова замолчать — это не баг, а особенность порога у этой модели.
- Живой тест на синтетическом юзере через боевой путь (`getCoachReply`, с tools): 1-й запрос — `cache_creation_input_tokens: 10812`, 2-й запрос тем же юзером — `cache_read_input_tokens: 10812`, `input_tokens` упал с 509 до ~500 (осталось только «Сейчас:» + новое сообщение). TTL — стандартный эфемерный (5 минут), не менял.

`.env` создан Артёмом вручную (не через меня — писать в `.env` мне запрещено технически, даже проверить наличие переменной нельзя). `TELEGRAM_BOT_TOKEN` и `ANTHROPIC_API_KEY` подтверждены рабочими (коуч отвечает).

Тестовый процесс бота — не через systemd, а руками (`setsid nohup node src/index.js`), отвязан от сессии, живёт между разрывами. Есть постоянная permission на рестарт этого процесса в рамках дев-сессии.

**Осторожно при тестировании (урок 11.09.2026):** НИКОГДА не импортировать/запускать `src/index.js` напрямую (`import('./src/index.js')`, `node src/index.js` из тестового скрипта и т.п.), если рабочий процесс бота уже запущен — `bot.launch()` открывает второй `getUpdates`-поллинг на тот же Telegram-токен, Telegram отвечает `409: Conflict`, и это роняет РАБОЧИЙ процесс (необработанное исключение). Для тестов — только импорт функций из `db.js`/`coach.js` напрямую, без `index.js`.

11.09.2026 (четвёртый заход) — фото еды (`bot.on('photo')`):
- Единственный явный пробел между MVP-спекой («Фото еды: в MVP входит») и кодом — фото раньше молча игнорировались.
- Модель — Haiku 4.5, тот же вызов `callCoach`, что и у текстового диалога (осознанно: одна модель — одно кэш-пространство, не ломает prompt-кэш). Сравнение Haiku/Sonnet на `research/test-photos/` не проводили — папка пустая, само сравнение не блокирует запуск.
- Картинка НЕ хранится в БД (разовая, большая, не нужна для памяти) — в `messages` остаётся только лёгкий текстовый плейсхолдер (`[Фото еды] <подпись>`), сама картинка идёт в Anthropic API только в момент запроса.
- `@anthropic-ai/sdk@0.32.1` (стабильный путь) поддерживает только `source:{type:'base64'}` для картинок, не `url` — код скачивает файл по `ctx.telegram.getFileLink` и кодирует в base64 сам.
- Берём предпоследний размер из `ctx.message.photo` (Telegram отдаёт от меньшего к большему) — «стандартное разрешение» из спеки. У Anthropic нет отдельного тумблера «high-res режим» для Vision — токены считаются по площади картинки, реальный рычаг стоимости это выбор размера файла.
- Бот НЕ считает калории/БЖУ в цифрах (прямо запрещено новой инструкцией в `FROZEN_INSTRUCTIONS`) — только качественная оценка, консистентно с позиционированием бота из спеки («не калькулятор калорий»). Структурированного лога питания в БД нет и не планируется в этом заходе.
- Живой тест (синтетический юзер, сгенерированный валидный 1×1 PNG, реальный вызов API): пайплайн отработал, модель корректно распознала нечёткое «фото» и попросила переснять вместо того, чтобы выдумать еду — сработала инструкция. Полноценный тест на реальном фото через Telegram — на Артёме.
- План реализации — `/home/agent/.claude/plans/dazzling-yawning-sunset.md`, там же обоснование дизайна.

11.09.2026 (шестой заход) — профиль без пересоздания анкеты + замеры тела + структурные поля бега. Три связанных, но независимых куска, план реализации — `/home/agent/.claude/plans/dazzling-yawning-sunset.md` (по 7 отдельным коммитам, каждый можно откатить не трогая остальные):
- **`/profile`** — команда показывает 8 полей анкеты + последние известные замеры (талия/грудь/бёдра, только чтение) + кнопки «Изменить: <поле>» на каждое. Кнопочные поля (goal/gender/activity/tone) переиспользуют существующий `buildQuestion`/анкетный `bot.action`, научили его отличать правку уже полного профиля от анкеты (`isProfileComplete`) — иначе после правки одного поля показывалось бы «Буду писать тебе каждый день…». Текстовые поля (age/weight/height/checkin_time) — новая колонка `users.pending_edit_field`, у них нет кнопочного callback-флоу.
- **Разговорная правка** — новый tool `update_profile`, коуч сам вызывает, если юзер явно сообщил об изменении анкетных данных в чате («мне вообще-то 32», «смени тон на мягкий»). `gender`/`activity`/`tone` — `enum` в схеме тула (не разъедется со значениями, которые использует остальной код), `age`/`weight`/`height`/`checkin_time` — через те же парсеры, что в анкете (`onboarding.js`, теперь экспортированы), невалидное значение тихо пропускается.
- **Замеры тела** — новая таблица `body_measurements` (append-only история, по образцу `fitness_tests`) + снимок последнего в `users` (`waist`/`chest`/`hips`, `weight` уже был). Tool `log_body_measurements`. Мягкое напоминание вплетено в обычный ответ коуча (НЕ отдельный push — сознательный выбор после обсуждения с Артёмом двух вариантов), интервал ~неделя, не гаснет навсегда как тест готовности (замеры регулярные, не разовые). Про грудь/бёдра — упоминается только в самом первом предложении за всё время, дальше не наседаем; юзер может прислать их сам в любой момент.
- **Структурные поля бега** — `training_log` расширен `distance_km`/`avg_pace_min_km`/`avg_hr` (TEXT, не новая таблица), специально спроектировано так, чтобы в будущем те же колонки заполняла синхронизация с Strava/Garmin/Apple (сама синхронизация — вне MVP, как и раньше, тут только поля под неё).
- Все три куска живо протестированы на синтетическом юзере (реальные вызовы API): замер ловится `log_body_measurements` и не путается с тренировкой; правка профиля через разговор — 3 поля по отдельности, ничего лишнего не задето; цифры пробежки корректно легли в новые поля `training_log`. `/profile` — нельзя протестировать синтетическим скриптом (нужны реальные callback-кнопки), живой прогон на Артёме.

17.09.2026 — тест DeepSeek как альтернативы Anthropic для диалога с коучем (экономия, тестируем перед решением о переходе):
- `LLM_PROVIDER=deepseek` в `.env` переключает `coach.js` на DeepSeek через их Anthropic-совместимый эндпоинт (`api.deepseek.com/anthropic`) — тот же SDK, тот же формат запроса (tools/messages/system), меняются только baseURL/ключ/модель (`deepseek-flash`). `cache_control` DeepSeek молча игнорирует, не ломает запрос.
- Живые тесты на синтетическом юзере (план тренировок, лог пробежки, тон на контексте «не выспался», вечернее закрытие дня, фото еды с нечёткой картинкой): DeepSeek в 2.5–27 раз дешевле Anthropic Haiku 4.5 по факту (`usage` с реальных вызовов), качество ответов сопоставимое, vision тоже работает (на нечётком фото корректно попросил переснять, не выдумал еду).
- **Находка:** DeepSeek иногда вызывает `update_plan`, но не сопровождает его текстом — юзер видел бы голое «Обновил план.» без расписания. Не проблема промпта (в описании tool'а это уже требовалось) — похоже на особенность модели. Фикс: fallback для `update_plan` теперь строит содержательный ответ из того, что реально сохранили (`describePlanUpdate` в `coach.js`), а не отдаёт заглушку. Ретрай на больший бюджет токенов (`COACH_MAX_TOKENS_RETRY`) теперь срабатывает и для этого случая. Работает независимо от провайдера.
- Решение о переходе на DeepSeek по умолчанию — не принято, `LLM_PROVIDER` по умолчанию остаётся `anthropic`. Держим неделю на наблюдении (временный лог `usage` за флагом `DEBUG_USAGE` в `callCoach`), потом сравним ещё раз и решим.
- Тестовый скрипт — `_tmp_test_deepseek.mjs` в корне проекта (не в git, набор сценариев через `node _tmp_test_deepseek.mjs <сценарий>`).

- Автосинхронизация с Strava/Garmin/Apple — вне MVP (см. «Ключевые решения»), поля в `training_log` уже готовы её принять

## Ключевые решения (не пересматривать без веской причины)

- Аудитория: русскоязычные релоканты в Сербии, Telegram-only на старте, сербский язык — фича на потом
- Гипотеза успеха MVP: ежедневное возвращение пользователя к разговору, не оплата (цена — вторичная гипотеза, 300-1000₽/мес)
- **Оплата модели (обновлено 09.09.2026):** решение от 08.09 про подписку/`askModel()` отменено. Заводим платный `ANTHROPIC_API_KEY` сейчас. `src/coach.js` уже вызывает `@anthropic-ai/sdk` напрямую — код менять не нужно, ключ подхватится из `.env` автоматически. Ключ Артём вписывает в `.env` сам (мне запрещено писать туда).
- Core loop: петля привычки — триггер (бот пишет первым) → минимальное действие → награда → план на срыв
- Тренировочные планы: гибрид — 2 профиля нагрузки на старте (выносливость, силовая), skill-методички курирует Артём вручную (веб-поиск по авторитетным источникам, НЕ GitHub), человек в цикле проверки обязателен
- Бот — conditioning/lifestyle-коуч (питание, разминка, восстановление), не тренер по технике конкретного спорта — под это не нужна экспертиза в каждом виде
- Фото еды — в MVP (стандартное разрешение, не high-res), реализовано 11.09.2026 — качественная оценка, без счёта калорий/БЖУ, без хранения картинки
- **Модели (обновлено 11.09.2026):** Haiku 4.5 для диалога с коучем. Дешевле Sonnet 5 вдвое, плюс с 11.09 работает prompt-кэш (кэш-чтение ~1/10 цены) — см. запись выше. Путаницу день↔тренировка, из-за которой 10.09 откатывались на Sonnet, теперь снимает не модель, а код: сведённый календарь + якорь на 3 дня. Если после живого теста Haiku всё равно поедет на краевых случаях — тогда Sonnet, но сначала фикс (учесть: у Sonnet другой порог кэша — 1024 токена вместо 4096 у Haiku, кэш не сломается). Для фото еды — Haiku 4.5 (vision есть), тест на реальных фото из `research/test-photos/` ещё не делали
- Память: простая БД на юзера, НЕ векторная база, НЕ отдельный сервер на человека
- Оплата в MVP — вручную, переводом, первым 20-30 знакомым

## Явно ВНЕ MVP — не предлагать без явного запроса Артёма

Viber/кроссплатформенность, геймификация с блокировкой приложений (нужно нативное приложение), подключение часов/Strava, автоматическая мультивалютная оплата, полностью автономная генерация плана моделью без ограничения категорий и без методичек

## Оценка сроков

3-4 недели по 1.5 часа в день (~20-25 сессий), при условии не отвлекаться на пункты выше
